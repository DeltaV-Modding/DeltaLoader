Safety & legal scope

Everything here applies to your own, legally acquired copy in single-player. The mapping contains only our own static observations - no game code, no assets.

Before every test: back up your save and use single-player. A mod runs in the same process as the game; a bug in the mod can crash the game.
No multiplayer, no anti-cheat. The bridge aborts as soon as it sees an anti-cheat module in the process (fail closed), and it does not modify game files. Do not load mods into other processes or onto other people's servers.

The version binding is intentional: if the running EXE does not match the mapping exactly (different build, update), your mod does not start at all - instead of corrupting something with wrong addresses.

Your first mod in three steps

  1. Get the SDK and install the requirements: Windows x64, CMake 3.20 or newer, Visual Studio 2022 with the C++ workload. 
    git clone https://github.com/DeltaV-Modding/DeltaLoader
  2. Write your mod in a .cpp file with #include "sw/mod.hpp", SW_MOD("your_mod"), sw_mod_start() and sw_mod_stop(), and register it in CMakeLists.txt: 
    sw_add_mod(your_mod src/your_mod.cpp)
  3. Build it. The DLL lands in build-mod/Release. 
    powershell -ExecutionPolicy Bypass -File build_mod.ps1
Load the DLL with DeltaLauncher: put it in <Stormworks>\mods\<Name>\ and enable the mod. Use single-player with a backed-up save.

Good to know

  • Everything your mod prints also lands in the log file %TEMP%\stormworks_mods.log - even without a console window.
  • If your game build does not match the mapping (SHA-256 or signatures), the bridge checks this inside the process and only starts your mod on complete success.

Structure and lifecycle of a mod

A mod is a DLL with exactly two functions that you write:

#include "sw/mod.hpp"

SW_MOD("my_mod")

void sw_mod_start() {               // runs on its own thread
    sw::mod::log("Hello from inside the game!");
    while (sw::mod::sleep(1000)) {  // false = mod is being unloaded
        // do something every second
    }
}

void sw_mod_stop() {                // just before unloading
}

The framework takes care of the rest:

  • Version check (SHA-256 + all 194 signatures). If the game does not match, sw_mod_start() is not called and the console says why.
  • Its own thread, so your code does not block the game.
  • Clean unload: on unload the framework stops the thread, calls sw_mod_stop(), removes all of your hooks and waits until no game thread is still inside a callback. Only then is the DLL released.

The exact load sequence

  1. The loader checks the target: correct bitness, matching process name, no anti-cheat module in the process, SHA-256 of the EXE.
  2. The DLL is loaded with regular LoadLibraryW - no EXE patch; once the game quits, nothing remains.
  3. The DllMain part of the framework starts your thread and checks: SHA-256 and all 194 byte signatures in memory. If anything is off, sw_mod_start() is not called, and the console names the reason.
  4. Only then sw_mod_start() runs on your thread alongside the game - until you set hooks, your code has no effect on game threads.

The exact unload sequence

  1. The loader (or the in-game mod menu) calls your DLL's export swmod_shutdown() - both exports come from the SW_MOD("...") macro.
  2. The framework sets running() to false, waits for your sw_mod_start() thread to end, calls sw_mod_stop() and removes all hooks of the mod.
  3. Then it waits until no game thread is still inside a callback of the DLL (sw::Hook::idle()) - only afterwards comes FreeLibrary.

If a callback is still busy inside the game (say, mid Lua frame with a sleep), unloading can be delayed by up to 5 s; after that the DLL is deliberately left loaded: a small leak beats a crash. The mod name (console, log file, mod menu) comes from SW_MOD("my_mod").

That is why this matters: loops must check sw::mod::sleep() or sw::mod::running(). Otherwise the mod cannot be unloaded and the unload waits in vain (5 s).

Hooks - reacting to the game

A hook intercepts entry into a game function. Your callback runs before the original code continues:

void cb(void* self, void* user);
  • self = first argument of the function. For a method that is this (the object); for a Lua handler it is the lua_State*.
  • user = the pointer you passed when installing the hook.

All game arguments (rcx, rdx, r8, r9 and xmm0-3) are preserved; afterwards the original code continues normally. Four ways to install a hook:

CallHooksself
rt.hook_api("server.getPlayers", cb, user, err) a Lua handlerlua_State*
rt.hook_ctor("c_scene_ropes", cb, user, err) every new object of a classnew object
rt.hook_method("class", slot, cb, user, err) a virtual methodthis
rt.hook_rva(rva, cb, user, err) any function1st argument

Why a hook can fail

Every call returns a status; on error nothing at the game has been changed, and err names the reason as text.

StatusMeaning
unsupported_archnot x64 - only the 64-bit game is supported
target_invalidthe target is not inside the executable main module (e.g. in your DLL or in data)
already_hookedthe same callback/user combination is already attached at this site
decode_failedthe first instructions cannot be relocated safely
relocation_faileda rel8 jump lies inside the overwritten range (5 bytes)
alloc_failed / write_failedmemory for stub/trampoline or the overwrite itself failed

Two requirements for a custom hook_rva target address: it must be a function start (rt.is_function_start() checks that), and the first bytes must be safely decodable. Both can be checked against the EXE file in advance - without a running game:

  • sw::Hook::plan(bytes, available, length, err) runs the same decoding for arbitrary bytes - writes nothing and needs no process.

The callback reads additional arguments with sw::Hook::arg(n): 0 = rcx, 1 = rdx, 2 = r8, 3 = r9, and from 4 onward from the stack - as they were on entry. sw::Hook::arg2() is shorthand for the second argument as a pointer. Both only work during the callback; floating-point arguments (xmm0-3) are not provided.

Rules for callbacks. They run in the middle of the game's code. Keep them short, do not block, do not throw exceptions. In a constructor callback the object is not finished yet - just remember the pointer; reading/writing belongs in the loop in sw_mod_start().

What the mechanism guarantees

  • All register arguments are preserved. The stub saves rcx, rdx, r8, r9 and xmm0-xmm3 before the callback and restores them afterwards; stack arguments are untouched anyway. The hook therefore fits functions with any parameter list.
  • The callback may live in your DLL. With ASLR it sits far away from the game module almost always (more than 2 GB); the stub therefore calls the callback through a pointer in its own page. Target, stub and trampoline are each directly connected.
  • Several callbacks per target (up to 32) are possible - useful when several classes share a constructor. The same callback with the same user is rejected.
  • Atomic overwrite of the first 5 bytes when they lie inside one aligned 8-byte block - the normal case, because functions begin on 16-byte boundaries.
  • No unwind-table backing: the stub is deliberately not in the unwind tables. If the callback itself threw an exception, the unwinder would see machine code it cannot interpret - so callbacks must not let exceptions escape.

The framework removes your hooks on unload itself. To remove a single one: rt.unhook(address, cb, user, err) or rt.remove_ctor(...).

Finding objects

Constructor hooks let you keep track of which objects of a class are currently alive:

std::string err;
sw::Instances::track("c_scene_ropes", err);     // start tracking

for (auto obj : sw::Instances::list("c_scene_ropes")) {
    auto name = sw::mod::rt().class_of(obj);     // actual class
    sw::mod::log("object 0x%llx", (unsigned long long)obj);
}
  • Objects created before track() are missing - so load the mod early or reload the scene.
  • list() filters dead objects heuristically (readable memory + known vptr). The destructor is not mapped, so check with rt.is_instance_of(obj, "class") before using an object.
  • Derived classes pass through the base class constructor and also appear in its list; class_of() reports the real one.

Building UI (UI mods)

Attaching your own elements to the game - rectangle, button, text - works through real engine constructors and in exactly the order the game uses when it builds its menus. The same order works for the main menu and the loading screen.

Elements and their addresses

Addresses change with every game build, so none are listed here. Look them up by name in the headers of the current SDK: sw/generated_symbols.hpp (RVA of every named function, e.g. the constructors of c_ui_element_rectangle and c_ui_element_text, the button factory, mm_string and the child-attach function) and sw/protos.hpp (the bound engine functions). The element layout below was measured on an older build; check offsets against the current build before you rely on them.

Fields of a UI element

The positions are proven in the live game - readable and writable with rt.readable() and write_bytes(), or directly:

OffsetFieldNotes
+0x08 / +0x0cx / y relative to the parent and its anchor; y points up
+0x10 / +0x14width / height
+0x18anchor (u32) see below
+0x1cvisible (u8) 0 = not drawn and not hit-tested
+0x20parent pointer
+0x30child list attach point for the child-attach function
+0x90action id (buttons only) evaluated by the menu on click; 0 = none
+0xd8 / +0xe0callback + user pointer (buttons only) on release the game (button slot 18) calls callback(input, user) if the button was pressed and +0x1d is set

Anchors (+0x18)

A value 0-8, evaluated by the layout code relative to the parent - both axes hang on the same number:

  • x = value mod 3: 0 = left, 1 = centered, 2 = right.
  • y = value divided by 3 (rounded down): 0 = at the top edge with your own y offset (base H - h), 1 = centered, 2 = fixed at the bottom edge (offset 0).

Since y points up, 0 = "top left" and 6 = "bottom left"; the examples stack menu rows by making y ever smaller.

Attaching: the same four steps the game uses

// 1. Create: memory via the engine, then the constructor
void* s = g_new(0x60);
const auto r = reinterpret_cast<std::uintptr_t>(
    g_rect(s, x, y, width, height, kAnchor, color));
// 2. Into the parent's child list (parent + 0x30)
g_addchild(reinterpret_cast<void*>(parent + 0x30), reinterpret_cast<void*>(r));
// 3. Call vtable slot 1: build; ctx comes from the rdx argument
//    of the build hook (main menu, loading screen)
// 4. parent + 0x20 = parent, then vtable slot 29: attach

Use exactly this order. The ctx belongs to exactly that screen build - cache it (e.g. in the build hook via sw::Hook::arg2()) and reuse it for building.

Strings: MmString

{ pointer, size, capacity }, 16 bytes. The buffer must be allocated through the engine - the game frees it later:

MmString s{};                        // { nullptr, 0, 0 }
g_reserve(&s, length + 1);           // allocate buffer
std::memcpy(s.data, text, length);
s.data[length] = '\0';
s.size = length;                     // length without the null byte
The button factory copies both strings and frees their buffers - your MmString may disappear afterwards. The text constructor takes ownership of the passed buffer; even then the buffer must come from the engine string allocator.

Threads while building UI

The build runs on the thread on which the game is currently building or ticking its surface (engine thread). The same rules as for any callback apply: keep it short, do not block, no exceptions.

  • In the build/tick only create, attach, read and write.
  • Anything slow (files, loading DLLs, window work) is handed over as a queued job that the loop in sw_mod_start() processes on the mod thread - exactly the pattern main_menu follows.
  • Communication between mod thread and engine thread only via atomics or mutex-protected queues.

What is not proven - and how the examples work around it

  • Changing the text of an existing element: not proven. The examples' trick: two elements at the same spot, toggle the right one visible (e.g. ON/OFF).
  • Removing elements: not proven. Example trick: move them far off screen (x + 100) - the hit test no longer finds them there.
  • Visibility: flip +0x1c between 0 and 1 - hides the element together with its children (what main_menu does too).

The launcher

DeltaLauncher (Tauri) installs mods from the catalog, builds the game start and loads the mods into the game.

Updates

The launcher updates itself silently: it downloads the new installer and runs it with /S /UPDATE /R, so no installer page appears and the launcher restarts. It also carries the loader files it needs and keeps them up to date.

Discord Rich Presence

On by default; the switch is in the launcher settings. The injected version patch talks to the local Discord pipe and shows the place (menu, world, editor), the number of loaded mods and the time played. The activity has two buttons; Discord shows buttons to other people only, never on your own profile.

Debug start (RenderDoc)

RenderDoc must start the game itself, which bypasses the mod loader. Settings → Debug start (RenderDoc) prepares the mods and the overlay, then waits for stormworks64.exe. Start the game from RenderDoc afterwards. Do not start the launcher itself under RenderDoc (its web view freezes).

Shader files are read at game start, so a shader mod needs the overlay start, not the virtual one.

Adding your mod

Each mod is one DLL. Register it in CMakeLists.txt; sw_add_mod links swmodkit for you, sets the static runtime (MultiThreaded) and the compiler flags /W4 /permissive- /utf-8:

sw_add_mod(my_mod src/my_mod.cpp)
# several files:
sw_add_mod(my_other_mod src/a.cpp src/b.cpp)

The DLL file name is the target name (no lib prefix). Build with powershell -ExecutionPolicy Bypass -File build_mod.ps1 or by hand: cmake -S . -B build-mod -G "Visual Studio 17 2022" -A x64 and cmake --build build-mod --config Release.

Requirements and rules

  • Windows x64, CMake 3.20 or newer, Visual Studio 2022 with the C++ workload, C++17.
  • Only stormworks64.exe is supported. The 32-bit game no longer exists.
  • Every mod needs SW_MOD("name") once and the two functions sw_mod_start() and sw_mod_stop().
  • Single-player only. Back up your save before testing.

Recipes

Short, complete patterns. Each one only uses calls that exist in the headers of this SDK (see the header reference for all signatures). Calls that talk to the game return false or nullptr when the game build does not match, so always check the result.

1. The smallest mod

#include "sw/mod.hpp"

SW_MOD("my_mod")

void sw_mod_start() {
    sw::mod::log("started");
    while (sw::mod::sleep(1000)) {      // false as soon as the mod is unloaded
        // work once a second
    }
}
void sw_mod_stop() {}

sw_mod_start() runs on its own thread. A loop must check sw::mod::sleep() or sw::mod::running(), otherwise unloading waits for it.

2. Hook a game function and count calls

#include "sw/mod.hpp"
#include <atomic>

SW_MOD("counter")
static std::atomic<int> g_calls{0};

static void on_call(void* self, void* user) {   // runs before the original code; keep it short
    ++g_calls;
}

void sw_mod_start() {
    std::string err;
    auto status = sw::mod::rt().hook_api("server.getTime", on_call, nullptr, err);
    if (status != sw::HookStatus::ok) {
        sw::mod::log("hook failed: %s (%s)", sw::to_string(status), err.c_str());
        return;
    }
    while (sw::mod::sleep(5000)) sw::mod::log("calls: %d", g_calls.load());
}
void sw_mod_stop() {}

hook_api takes a Lua API name from the mapping. Other entry points: hook_ctor(class, ...) for constructors, hook_method(class, slot, ...) for virtual methods, hook_rva(rva, ...) for a known address. A callback reads integer arguments with sw::Hook::arg(n) and cannot change them. Hooks are removed when the mod unloads.

3. Find living objects of a class

std::string err;
sw::Instances::track("c_scene_ropes", err);                 // once, in sw_mod_start
for (auto obj : sw::Instances::list("c_scene_ropes")) {      // later, any time
    sw::mod::log("rope object at %p", (void*)obj);
}

4. Weather and time

#include "sw/mod.hpp"
#include "sw/weather.hpp"

SW_MOD("storm")
void sw_mod_start() {
    if (!sw::weather::watch()) { sw::mod::log("weather: game does not match"); return; }
    while (!sw::weather::ready() && sw::mod::sleep(500)) {}   // waits until the environment object was seen
    sw::weather::set_weather(0.8f, 0.9f, 0.7f);            // fog, rain, wind (local only)
    sw::weather::TimeOfDay t;
    if (sw::weather::time_of_day(t)) sw::mod::log("it is %02d:%02d", t.hour, t.minute);
    while (sw::mod::sleep(1000)) {}
}
void sw_mod_stop() {}

The writers change the local game state like the game's own handler; other players are not told. The sampler only uses the "current" values while the setting override_weather is on.

5. Draw or set a shader uniform each frame

#include "sw/mod.hpp"
#include "sw/render.hpp"

SW_MOD("uniform_demo")
static void on_frame(void* window, void* user) {          // render thread, GL context current
    float v[3] = {1.f, 0.5f, 0.f};
    sw::render::set_uniform("my_color", v, 3);               // every program that declares my_color
}
void sw_mod_start() {
    if (!sw::render::watch()) return;
    sw::render::on_frame_end(on_frame, nullptr);
    while (sw::mod::sleep(1000)) {}
}
void sw_mod_stop() { sw::render::remove_callbacks(); }

A uniform belongs to a program object and keeps its value. Declare it in a shader of your own mod folder (Graphics\shaders, which needs the overlay start of the launcher); the game only sets the uniforms its own shader classes know.

7. Rules that prevent most crashes

  • Check every return value; a mismatching game build returns false/nullptr and nothing else happens.
  • Callbacks run on game threads. Keep them short; hand slow work to the mod thread.
  • Use the engine allocator for objects the game frees; never malloc them.
  • Never write game memory you cannot name. write_bytes/write_rva exist but are for single-player experiments.
  • After a game update mods stop on purpose until the SDK is updated.

//    is kept in a slot. gl_function() returns what the game loaded. 59 of them are used by
//    the engine; the 43 functions of OpenGL 1.1 come through the import table of OPENGL32.dll.
//  * The renderer object (constructor 0x6d16c0) holds 80 shader objects at fixed offsets.
//    The frame function 0x6d4de0 (36 KB) runs, in the order of its code: the depth downsample
//    and SSAO, the scene, then temporal AA (shader temporal_aa), motion blur, tonemap and
//    FXAA. The engine already has what a temporal upscaler needs: a velocity texture
//    (texture_velocity), the depth, the colour of the last frame and a per-frame offset
//    (rand_offset, the jitter) - see shader_inputs in the mapping.
//
// THE PIPELINE (REPORT 3.113). The renderer is deferred. One view ("pipeline", 0x66e3a0 builds it)
// owns these targets: [0] the G-buffer (RGBA16F, RGBA8, RG16F = the VELOCITY, depth/stencil),
// [1] the lit scene colour (the `light` shader composes the G-buffer into it), [2] the history
// of the last frame, [3] the output of the anti-aliasing, then SSAO, bloom, and small ones. The
// anti-aliasing mode is a field of the pipeline (1 = FXAA, 2 = temporal AA). In mode 2 the pass
// 0x68fde0 reads [1] (colour), [0] attachment 2 (velocity) and [0] depth, the history [2] and
// writes [3]; the tonemap then reads [3] and DRAWS TO THE SCREEN (framebuffer 0) at the window
// size. There is no separate final blit. An upscaler therefore goes between the scene colour
// and the tonemap: read upscaler_inputs(), write `output_texture`. upscaler_inputs() delivers
// exactly the OpenGL ids a temporal upscaler needs. The jitter is NOT in the engine:
// `rand_offset` of the TAA is two CRT rand() values (noise for the filter), the projection
// is not jittered; a temporal upscaler has to add its own.
//
//   #include "sw/render.hpp"
//
//   sw::render::watch();                                 // once, in sw_mod_start
//   sw::render::on_frame_end(my_overlay, nullptr);       // runs on the render thread, GL context current
//   void* fn = sw::render::gl_function("glBindFramebuffer");
//
// RENDER TARGETS (REPORT 3.112). Every framebuffer of the renderer is an object of the family
// mm_resource_target_* (target, multiple, multisample, mipmapped). watch_targets() hooks the
// functions that create and delete their OpenGL objects and keeps the list, so targets()
// returns every live target with its OpenGL framebuffer, colour and depth texture ids, size
// and format. The size of the main view is the client area of the window; there is no render
// scale setting (graphics state + 0x8f0 / 0x8f4). The last use of the scene target is a blit
// to framebuffer 0 (slot 4 of the class); that is the place for an upscaler to take over.
//
// ABOUT DLSS. NVIDIA's DLSS SDK has no OpenGL backend (Direct3D 11/12 and Vulkan only), and
// this game is OpenGL. So there are three honest ways: (1) a spatial upscaler written as an
// OpenGL shader in the place of the FXAA pass (FSR 1 style; needs nothing the engine lacks);
// (2) a temporal upscaler (FSR 2 style) in the place of temporal_aa, which gets the velocity,
// depth and jitter the engine already has; (3) DLSS itself through a shared texture between
// OpenGL and Vulkan/D3D (GL_EXT_memory_object or WGL_NV_DX_interop2) - heavy, and the colour,
// depth and velocity have to be copied out and the result back. This header gives the base
// for all three: the frame end, the GL entry points, the pass order and the shader offsets.
// It does not contain an upscaler.

C++ runs in-game

C++ is the main route for mods that run inside the game process. The entire section above describes it. In short:

#include "sw/mod.hpp"
SW_MOD("my_mod")

void sw_mod_start() {
    auto& rt = sw::mod::rt();
    std::string err;
    rt.hook_api("server.getPlayers", [](void*, void*){
        sw::console::print("getPlayers called\n");
    }, nullptr, err);
    while (sw::mod::sleep(500)) { }
}
void sw_mod_stop() {}

build_mod.ps1 builds your mod. x64 only (stormworks64.exe).

Troubleshooting

SymptomCause / solution
Mod does not start, console reports a SHA-256 mismatch The game version does not match the mapping. Wait for the SDK update for the new build.
Build failsRead the compiler errors in the terminal; check the requirements (CMake 3.20+, Visual Studio 2022 C++ workload, x64).
Game crashes in mod codeCallback too long, throws an exception, or uses an object before is_instance_of.
Game quits immediately (exit code 5)An anti-cheat module is in the process - multiplayer and dedicated servers are off-limits.
Hook does not install, err names a status The meaning is in the hooks table; check a custom target in advance with rt.is_function_start().
"a callback is still running", DLL stays loaded Safety net, not an error: a game thread is still inside a callback (long work without checking sw::mod::sleep()). Keep callbacks short, move slow work to the mod thread.
Console stays empty in-gameOutput always lands in %TEMP%\stormworks_mods.log - look there (sw::console::log_path()).

Limits

  • Only stormworks64.exe (x64). The game and the dedicated server are 64-bit only since v1.15.25.
  • No field names: the mapping knows classes, vtables and constructors, but not what a field is called - only its position.
  • Arguments and return values of a Lua handler are not described; the hook provides the lua_State*, not the parameters.
  • No destructors mapped: "is this object still alive?" is a check (memory readable, vptr points at a known vtable), not knowledge - sw::Instances could theoretically let a reused memory block slip through. Always check with rt.is_instance_of() before using an object.
  • resolve() returns an address, not a parameter signature - establish the call convention on-site in your own mod, do not infer it from the mapping.
  • Processes with anti-cheat are never touched; the bridge is deliberately fail-closed (SHA-256 + all 194 signatures must match, or nothing is delivered).
  • A game update changes the binary - then no mod starts until the mapping is regenerated.
